# xv6 Kernel Extensions

> 시스템 콜부터 스케줄러와 가상 메모리까지 xv6의 핵심 실행 경로를 직접 확장한 학부
> 운영체제 기술 사례

## 해결한 기술 문제

### 1. 사용자 호출을 커널 기능으로 연결

`getppid`를 위해 시스템 콜 번호, dispatcher, kernel handler, user header와 assembly stub을
함께 확장했습니다. 단일 함수 구현이 아니라 user mode에서 kernel mode까지 연결되는
시스템 콜 전체 경로를 다뤘습니다.

### 2. 우선순위와 공정성을 함께 반영

가장 낮은 nice 값을 우선 선택하고, 같은 nice 값을 가진 프로세스는 RUNNABLE 전환
순번으로 FCFS 선택했습니다. `fork`, `yield`, `wakeup`, `kill`에서 순번이 갱신되도록
프로세스 상태 전환을 추적했습니다.

### 3. 가상 주소 확장과 물리 할당을 분리

`sbrk`에서는 프로세스 크기만 확장하고 실제 접근이 발생했을 때 page fault handler가
페이지를 할당·초기화·매핑하도록 변경했습니다.

## 재검토에서 확인한 개선점

과제 2의 타이머 비선점 정책과 달리 보존 코드가 타이머 인터럽트 후에도 `yield()`를
호출하는 점을 확인했습니다. 타이머에 의한 자동 양보만 제거하고 명시적 `yield`와
`setnice`의 재선택 동작은 유지했습니다. 먼저 RUNNABLE이 된 프로세스가 일정 시간 CPU를
유지하는지를 구분해 확인하는 독립 테스트도 추가했습니다.

주소 범위 검사, 메모리 부족 처리, sparse address space의 `fork`는 과제 3의 기본
요구사항을 넘어서는 후속 견고성 개선 항목으로 분리했습니다.

## 문제해결 과정

1. 과제 명세를 시스템 콜, 선택 정책, CPU 반납 조건으로 나누어 실제 코드와 대조했습니다.
2. nice 우선순위와 동일 nice FCFS 선택은 구현되어 있었지만, 타이머 인터럽트 뒤의
   `yield()`가 비선점 조건과 충돌하는 것을 확인했습니다.
3. 우선순위 선택과 선점 여부를 혼동하지 않도록, CPU-bound 프로세스가 일정 시간 CPU를
   유지하는지를 확인하는 독립 테스트를 분리해 구성했습니다.
4. 정책에 어긋나는 타이머 기반 자동 `yield()`만 제거하고, 명시적 `yield` 및 `setnice`
   이후 재선택처럼 필요한 CPU 반납 경로는 보존했습니다.
5. 수정 후 과제 명세와 호출 경로를 다시 대조하고, 당시 실행 기록과 2026년 독립 검증
   코드를 서로 다른 근거로 구분했습니다.
